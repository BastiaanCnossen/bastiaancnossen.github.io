# Publishing generated notes

The website repository owns public deployment paths. A notes repository owns
its source, generator, and validated candidate bundle. Publication is the
explicit boundary between them.

## Normal workflow

From the notes repository, first run its complete production build. Then, from
this repository, run:

```powershell
.\publish-notes.ps1 -WorkId topos-theory -CheckOnly
.\publish-notes.ps1 -WorkId topos-theory
```

Use `-WorkId stable-homotopy-higher-algebra` for the SHT+HA web edition. Its
production candidate is generated by `build-web.ps1` in the book repository.

The publisher itself has isolated regression fixtures. Run them with:

```powershell
.\test-publication.ps1
```

The check-only command performs the complete preflight with a staged web bundle,
PDF, and lockfile without changing the live website. The publication command
then performs the same checks and replaces `notes/topos-theory/`,
`notes/topos-theory.pdf`, and the lockfile as one recoverable transaction.

## Work configuration

Every published work has one configuration in `works/<work-id>.json`. For
example:

```json
{
  "SchemaVersion": 1,
  "WorkId": "topos-theory",
  "SourceBundle": "../Notes/Topos theory/output/web",
  "SourcePdf": "../Notes/Topos theory/output/pdf/Notes higher topos theory.pdf",
  "PublicDirectory": "notes/topos-theory",
  "PublicPdf": "notes/topos-theory.pdf",
  "PublicBase": "/notes/topos-theory/",
  "Lockfile": "publication/locks/topos-theory.json",
  "Retirements": "publication/retirements/topos-theory.json"
}
```

`WorkId` is permanent once the work is public. The intended ID for the Stable
Homotopy Theory and Higher Algebra textbook is
`stable-homotopy-higher-algebra`. A new work receives its own configuration,
lockfile, retirement registry, web directory, and sibling PDF. Entry, section,
and chapter IDs are scoped by the work's public base and therefore need not be
globally unique across different works.

## Public-address contract

Each candidate bundle supplies `_meta/public-contract.json`. It records its
current work, section, entry, and alias routes, together with the explicitly
stable LaTeX-label, proof, and authored proof-detail fragments.

`locks/topos-theory.json` is cumulative. It records every route and promised
fragment that has reached the public website, including retired addresses. It
is generated by the publisher and should not be edited by hand.

The publisher fails before changing the live directory when a locked address
is missing from the candidate without an explicit rule in
`retirements/topos-theory.json`. This makes accidental registry renames,
deleted entries, and removed proof-detail IDs visible during preflight.

## Intentional retirement

Route rules use a full public path and either `redirect` or `tombstone`:

```json
{
  "Path": "/notes/topos-theory/entry/old-id/",
  "Action": "redirect",
  "Target": "/notes/topos-theory/entry/new-id/",
  "Added": "2026-08-25",
  "Reason": "The old entry was merged into the new entry."
}
```

A tombstone omits `Target`. The publisher generates a permanent explanatory
page at the retired route.

Fragment rules identify both their route and fragment. An alias target includes
its destination fragment:

```json
{
  "Path": "/notes/topos-theory/entry/example/",
  "Fragment": "old-detail-id",
  "Action": "alias",
  "Target": "/notes/topos-theory/entry/example/#detail-example--new-detail-id",
  "Added": "2026-08-25",
  "Reason": "The proof detail received a more precise permanent name."
}
```

Use `tombstone` when no mathematical replacement exists. Fragment notices are
shown only when their old hash is visited. Alias rules redirect the browser to
the replacement while retaining a no-JavaScript notice at the old fragment.

Retirement rules are permanent records. Keep them after the first publication
that uses them.

## Failure safety

The publisher copies the candidate web bundle and PDF to sibling staging paths,
materializes retirements, validates the staged files and all locked addresses,
and writes a staged lockfile. It then swaps the site directory, PDF, and lockfile.
If any replacement fails, it restores the preceding three artifacts.

The transaction uses deterministic staging and backup names. The lockfile
records hashes of both the web bundle and PDF. If the publishing process is
terminated during the swap, the next run verifies those hashes and either
completes the staged publication or restores the preceding web bundle, PDF, and
lockfile before doing new work.

The website remains a static site. This machinery runs only while maintaining
the repository. Readers receive ordinary files, with no database or server-side
application involved.

## Shared reader shell

`reader-shell-v1/` is the canonical visual frame for mathematical web editions.
It contains the shared stylesheet and small renderers for the return link,
manuscript PDF control, page header, utility dock, and responsive contextual
navigation toggle. Manuscript repositories import those renderers at build time
and copy the stylesheet into their own candidate bundles.

The shell does not contain theorem conversion, proof logic, mathematical macros,
or manuscript-specific navigation data. Breaking interface or class-name
changes require a new versioned shell directory so that each manuscript can be
migrated explicitly.
